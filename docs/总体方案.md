# Loop 总体方案

## 目标

Loop 是一个本机 Web 开发工作台。它先持续澄清用户问题，将需求、架构、接口、计划与验收标准固化为 Markdown，再由主 Agent 建立任务树、派发子 Agent、验证结果并完成集成优化。

模型 API 不被假设拥有自我迭代能力。每次模型调用只产生一个结构化动作，应用状态机负责保存上下文、执行动作、判断质量门槛并决定下一轮。

## 技术架构

- 前端：React、Vite、TypeScript，自定义组件与 CSS design tokens。
- 后端：Node.js、Fastify、TypeScript，绑定 `127.0.0.1`。
- 数据：Node SQLite，使用追加式事件记录和查询投影。
- 模型：OpenAI Responses API、DeepSeek Chat Completions，通过统一适配器归一化。
- 工作区：用户明确选择的项目根目录；读写、搜索、命令与 Git 操作均携带项目、任务、文档版本和幂等键。
- 隔离：执行阶段使用 Git worktree；非 Git 项目可以完成澄清和文档，但必须批准初始化后才能执行。

## Agent 工作流

运行状态依次为：`intake → clarifying → doc_review → ready → decomposing → executing → integrating → verifying → awaiting_acceptance → completed`，另有可选 `optimizing` 与 `paused`、`failed`、`cancelled`。验证通过只代表系统具备交付条件；只有用户选择保留分支或合并后才算完成。

每个 Agent 单轮只允许返回：向用户提问、提出文档修订、派发任务、调用工具、完成任务、暂停或请求上下文交接。调度器校验权限、预算、文档版本和任务依赖后执行一个原子效果，并写入事件记录。

Lead Main 持有全局文档与最终集成权。并行 Main 只能管理获租约的互斥模块。技术 Alpha 默认固定模型、单 Lead、并发 2、树深度 1、Agent 总量 12、直属任务 8；自动路由、更深任务树和高并发保留为实验配置，硬上限仍由服务端约束。

上下文预计达到模型窗口 75% 时，在原子操作完成后写入 `docs/runs/<runId>/handoffs/` 检查点。检查点包含文档哈希、任务树、模块状态、决策、验证证据、未决问题和下一步。旧实例撤销租约，继任实例校验检查点后恢复。

## 文档驱动

本目录五份核心文档是产品规范来源。批准状态和标准化内容哈希保存在数据库中；运行时任务必须声明引用的文档和版本。文件监听发现批准文档改变时，相关任务在安全点暂停并回到文档评审。

运行状态保存在 SQLite，但需求、决策、任务结果、验证证据和 Agent 交接必须能导出为 Markdown，确保模型上下文耗尽或服务器重启后仍可恢复。

## 安全边界

- 服务器只接受同源、带会话令牌的 localhost 请求，不开放 CORS。
- 所有路径经过绝对路径、真实路径和父目录校验，拒绝 `..`、符号链接、junction、ADS 与未授权 UNC 逃逸。
- `.git`、`.env*`、私钥、凭据目录和高置信度密钥内容不进入模型上下文；项目可用根目录 `.loopignore` 继续收窄读取范围。仓库文本一律标记为不可信数据，不能改变服务端权限。
- 分级审批默认允许经过外发策略的读取和任务内文件编辑；仓库 `package.json` 验证脚本、安装、联网、删除、Git 历史重写、推送和最终合并都需要逐次批准。
- 全自动模式仍不得绕过项目外写入、根目录删除、提权、凭据读取、外部发布和支付等硬安全线。
- API 密钥保存在 Windows 凭据管理器；环境变量为回退；日志和接口永不返回原始密钥。

## 当前实现基线

- 共享 Zod 契约、Fastify API、SQLite 投影、React 三视图和文档监听已经贯通；数据库 schema 当前为 7，并保持事务化单调迁移。
- 运行可从澄清进入文档批准、任务拆分、隔离 worktree、并发 Agent、集成脚本审批和全局验证；最终合并再次锁定来源分支、验证提交、目标分支与基线并逐次审批。本地演示模式必须显式选择，不调用模型，也不会伪造业务代码变更。
- 自动路由把 Lead 模型与 `allowedProviderIds` 分开保存，子任务只能从已配置、已启用且获准的供应商中选择。
- 启动快照携带 `snapshotVersion` 与事件水位，SSE 通过 `after`/`Last-Event-ID` 增量通知；审批公开风险、能力、资源和可复用性，高风险能力只能批准一次。
- 每个模型动作先写入 `ActionAttempt`，审批、工具输出、预算预留和任务结果均与 generation 关联；重启后只恢复已知安全点，结果未知的执行中动作不会自动重放。
- 集成要求当前 generation 的根任务、验证结果与 artifact 精确一一对应，按登记 commit SHA 合并；验证脚本前后 HEAD 与 worktree 必须保持不变。

## 架构优化方向

1. P0：为 `ACTION_OUTCOME_UNKNOWN` 增加人工核对与“确认已完成/安全重试”向导，避免只能检查数据库和 worktree。
2. P1：将供应商价格、能力、上下文窗口和限流状态改为可刷新元数据，替换技术 Alpha 的保守估算费率。
3. P1：增加真实任务基准集与简单/多 Agent 对照指标，达到接受率和成本门槛后再提升多 Agent 默认级别。
4. P1：为过期 worktree 清理提供 UI 预览、立即清理和保留期覆盖；孤儿分支仍不得静默删除。
5. P2：桌面封装、远程执行、多用户、图片和跨平台继续保持在当前安全模型之外。
