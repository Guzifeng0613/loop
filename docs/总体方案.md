# Loop 总体方案

## 目标

Loop 是一个本机 Web 开发工作台。它先持续澄清用户问题，将需求、架构、接口、计划与验收标准固化为 Markdown，再由主 Agent 建立任务树、派发子 Agent、验证结果并完成集成优化。

模型 API 不被假设拥有自我迭代能力。每次模型调用只产生一个结构化动作，应用状态机负责保存上下文、执行动作、判断质量门槛并决定下一轮。

## 技术架构

- 前端：React、Vite、TypeScript，自定义组件与 CSS design tokens。
- 后端：Node.js、Fastify、TypeScript，绑定 `127.0.0.1`。
- 数据：Node SQLite，使用追加式事件记录和查询投影。
- 模型：OpenAI Responses API、DeepSeek Chat Completions，通过统一适配器归一化。
- 工作区：用户明确选择的项目根目录；读写、搜索、命令与 Git 操作均携带项目、任务、文档版本和幂等键。
- 隔离：执行阶段使用 Git worktree；非 Git 项目可以完成澄清和文档，但必须批准初始化后才能执行。

## Agent 工作流

运行状态依次为：`intake → clarifying → doc_review → ready → decomposing → executing → integrating → verifying → optimizing → completed`，另有 `paused`、`failed`、`cancelled`。

每个 Agent 单轮只允许返回：向用户提问、提出文档修订、派发任务、调用工具、完成任务、暂停或请求上下文交接。调度器校验权限、预算、文档版本和任务依赖后执行一个原子效果，并写入事件记录。

Lead Main 持有全局文档与最终集成权。并行 Main 只能管理获租约的互斥模块。每个 Main 最多直属分发 30 个子 Agent；默认树深度 2、硬上限 4；默认总量 60、硬上限 200；并发默认 8，可配置 1–16。

上下文预计达到模型窗口 75% 时，在原子操作完成后写入 `docs/runs/<runId>/handoffs/` 检查点。检查点包含文档哈希、任务树、模块状态、决策、验证证据、未决问题和下一步。旧实例撤销租约，继任实例校验检查点后恢复。

## 文档驱动

本目录五份核心文档是产品规范来源。批准状态和标准化内容哈希保存在数据库中；运行时任务必须声明引用的文档和版本。文件监听发现批准文档改变时，相关任务在安全点暂停并回到文档评审。

运行状态保存在 SQLite，但需求、决策、任务结果、验证证据和 Agent 交接必须能导出为 Markdown，确保模型上下文耗尽或服务器重启后仍可恢复。

## 安全边界

- 服务器只接受同源、带会话令牌的 localhost 请求，不开放 CORS。
- 所有路径经过绝对路径、真实路径和父目录校验，拒绝 `..`、符号链接、junction、ADS 与未授权 UNC 逃逸。
- 分级审批默认允许读取和批准任务内的项目文件编辑；安装、联网命令、删除、Git 历史重写、推送和最终合并需要批准。
- 全自动模式仍不得绕过项目外写入、根目录删除、提权、凭据读取、外部发布和支付等硬安全线。
- API 密钥保存在 Windows 凭据管理器；环境变量为回退；日志和接口永不返回原始密钥。
