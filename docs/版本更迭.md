## 下一阶段优先级

1. P0 恢复体验：动作结果未知、冲突和基线漂移的人工核对向导。
2. P0 真实试点：至少 20 个 Git Node/TypeScript Web 任务，记录接受率、时间、费用和干预次数。
3. P1 规模验证：万级事件、百任务、长文档和 16 并发的性能/内存/磁盘压测。
4. P1 可运维性：完整生成式 OpenAPI、迁移回滚演练、诊断与故障排查文档。
5. P2 产品扩展：桌面封装、图片输入、远程执行和多用户在新的威胁模型批准前保持冻结。

## 2026-07-17 Alpha 优化记录

本轮收敛目标是让技术 Alpha 更接近真实可用，而不是扩大能力面。已完成并提交 `e7ec194 Harden alpha delivery workflow`，重点包括结构化命令安全门禁、动作级恢复、用户验收闭环、分页/SSE 契约、OpenAPI 暴露、worktree artifact 约束、窄屏与审批 UI、以及对应测试覆盖。

验证证据：

- `npm.cmd run lint`
- `npm.cmd run typecheck`
- `npm.cmd test`：8 个测试文件、74 个测试通过。
- `npm.cmd run build`

继续优化时优先保持以下判断：

1. 不把多 Agent、远程执行、图片输入、多用户或跨平台封装升为默认能力，直到真实任务验收率和成本数据证明简单模式已经不足。
2. 恢复链路下一步应围绕“人工可理解、可继续、可放弃”设计，而不是只补更多自动重试；动作结果未知、冲突、基线漂移和迁移失败都需要同一套诊断视图。
3. API/SSE 继续以 `@loop/contracts` 为唯一来源推进，后续重点是生成 OpenAPI 与客户端类型，避免手写 DTO 在前后端漂移。
4. UI 下一步应优先做真实工作流摩擦点：失败定位、审批影响范围、tool output 加载、脏草稿保护和移动端入口；视觉扩张低于可达性与任务完成率。
5. 规模压测要在可靠恢复稳定后做，否则只会测出已知恢复缺口；压测指标至少包括事件重放延迟、bootstrap 体积、SSE 断线重放、worktree 磁盘占用和预算预留一致性。

## 兼容与迁移

- SQLite schema 使用单调递增版本和事务迁移，不自动降级。
- Markdown front matter 的 `loop_schema` 独立于应用版本；旧 schema 先转换草稿，用户确认后批准。
- Provider 模型 ID 始终由用户配置，升级应用不静默更换模型。
- 后续版本再开放图片输入、跨平台桌面封装、远程执行、多用户和更多供应商。
